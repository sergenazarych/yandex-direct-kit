# Пакет изменений и журнал

Используй `references/CHANGES.md` базового `yandex-direct`, его команды записи и журнал `journal/<кабинет>/audit-log.jsonl`. Соблюдай подтверждение именно показанного пакета из `SKILL.md` этого скилла. Проверь, что журнал доступен для записи и доступ к кабинету разрешает операцию. Сначала выполни команды с `--dry-run --json`.

## Маршруты записи

Примеры рассчитаны на `yandex-direct` и читают реальное состояние только при подстановке настоящих кабинета и ID. `--help` показывает возможности установленной версии. Перед записью проверь ограничения типа кампании и актуальность API.

| Действие | Команда dry-run из каталога `yandex-direct` | Что проверить |
|---|---|---|
| Исключить площадки | `uv run scripts/campaign_write.py sites --account example --campaign 123 --add --site site.example --dry-run --json` | Это `ExcludedSites` кампании. Передавай каждую точную площадку отдельно, повторяя `--site`. Убедись, что API принимает идентификатор площадки, лимит позволяет добавить все позиции, существующий список сохранится. |
| Прочитать корректировки | `uv run scripts/bids.py modifier list --account example --campaign 123 --json` | Сверь область, сочетания пола и возраста, ID, `Enabled` и настройки затронутых групп. Для группы используй `--group`. |
| Добавить демографическую корректировку | `uv run scripts/bids.py modifier add --account example --campaign 123 --demographics AGE_0_17=0 --dry-run --json` | Добавляй отсутствующий срез. `AGE_55` означает 55+. Формат пола и возраста `GENDER_FEMALE:AGE_25_34=200`. Для новой корректировки группы укажи `--group` вместо `--campaign`. |
| Изменить имеющийся коэффициент | `uv run scripts/bids.py modifier set --account example --modifier 456 --value 200 --dry-run --json` | Перепроверь владельца ID, область, состояние `Enabled` и совместимость значения. Группируй несколько ID с одинаковым согласованным коэффициентом, если у них одинаковый смысл. |
| Поставить корректировку на устройства | `uv run scripts/bids.py modifier add --account example --campaign 123 --mobile 200 --os ANDROID --dry-run --json` | Проверь имеющиеся настройки уровня кампании и групп и пересечение типов устройств. Для существующей корректировки используй `modifier set`. |
| Обновить регионы группы | `uv run scripts/ads_write.py group update --account example --group 789 --region 213 --dry-run --json` | Пример оставляет единственный регион 213. `--region` передаёт полный список `RegionIds`. Используй справочник географии и сохрани остальные включения и исключения, учти вложенность регионов и расширенный геотаргетинг. Перечисли все фактические изменения охвата при согласовании. |
| Поставить объявление на паузу | `uv run scripts/ads_write.py ad suspend --account example --ad 987 --dry-run --json` | Проверь связь `AdId` с группой и кампанией, текущий статус и что остановка не погасит полезные комбинации или весь показ группы без согласия. Передавай точные `--ad`. |

В API корректировка `−100%` из интерфейса кодируется `0`, `+100%` — `200`, нейтральный множитель — `100`. Принятие значения зависит от типа корректировки. Например, региональный коэффициент имеет минимум `10`; исключение региона делай через `RegionIds` с учётом иерархии. Если показанный в отчёте срез уже отключён или переопределён группой, проверь даты статистики и фактическую область действия. В смешанной кампании изменение объявления, группы или коэффициента может затронуть поиск. Включи это в показанный пользователю объём изменения. [BidModifiers](https://yandex.ru/dev/direct/doc/ru/objects/bidmodifier) · [Допустимые коэффициенты](https://yandex.ru/dev/direct/doc/ru/bidmodifiers/set) · [AdGroups.update](https://yandex.ru/dev/direct/doc/ru/adgroups/update).

## Жизненный цикл пакета

1. **План.** Для планируемого пакета создай локальную запись рядом с рабочими материалами кампании. Укажи ID плана, кабинет, кампанию, период/цели/атрибуцию, ссылки на отчёты, список пунктов с ID объектов, доказательства и данные dry-run «было → станет». Для обратимости сохрани точные прежние настройки. Исключи из пакета действия без поддерживаемого API и проверяемого объекта. Покажи план пользователю. Сохраняй журналы и выгрузки в приватной рабочей папке.
2. **Согласование.** Привяжи ответ пользователя к ID плана и согласованным пунктам. Перед записью повтори dry-run и сравни текущие объекты, значения и реальные области действия с показанным планом, включая посторонние настройки, которые передаются полным списком. Существенные расхождения требуют нового согласования затронутых пунктов. Исполненные ранее пункты проверь и отметь, избегая повторной отправки. Для одного объекта подготовь единственную согласованную версию каждого меняемого поля.
3. **Применение.** Укажи `--apply` вместо `--dry-run` в согласованных командах. Выполняй последовательность за один заход, совмещая совместимые изменения и соблюдая зависимости. Процедура базового скилла сохраняет состояние до записи, проверяет его перед запросом, перечитывает состояние и пишет результат в журнал. Несколько API-вызовов могут завершиться частично. При тайм-ауте или неизвестном результате сначала перечитай объект и журнал. При расхождении, потере доступа или ошибке журнала останови затронутые и зависимые операции, сохранив результаты уже обработанных пунктов. Возобновляй только по текущему состоянию и действительному согласованию. Откат является отдельной правкой.
4. **Сверка.** Для каждого пункта запиши время со смещением часового пояса, объект, подтверждённые значения «было → запрошено → стало», результат и RequestId при наличии. Сошлись на штатном журнале и его строках; результат, принятый API без подтверждения повторным чтением, пометь как непроверенный. В сводке пакета зафиксируй также отказанные, пропущенные и неприменимые пункты. Если строка штатного журнала отсутствует после записи, зафиксируй восстановленное из API состояние и ошибку журнала в записи пакета. В ответе перечисли подтверждённые изменения и остаток, укажи пути к обоим журналам и окно проверки статистики.
